# Account baseline (Phase 0 reads)

What to read before the interview, and how to interpret each result. The goal is that the interview confirms rather than interrogates.

## Two disciplines that decide how Phase 0 goes

**Issue these reads as one parallel batch, not one call at a time.** Nothing in the list below depends on anything else in it, and serialising them is the single biggest reason Phase 0 drags. Fire the health, tenant, tool-list, user, integration-status and structure reads together, then read the results in one pass. Only follow-ups that genuinely need an ID from a first result (workspace members, per-user detail) go in a second batch. Tell the customer you are reading the account and then go quiet, rather than narrating each call.

**Count, do not fetch.** `distribution-list-put` and `rule-list` default to 200 full records and are large on any tenant with history. In Phase 0 you want shape, not contents: page size 1 for a count, then scope everything to the chosen workspace. Same discipline for schemas: read `schemaTokens` from `search-tools` before calling `describe-tools` on anything. Both are in `build-patterns.md` § Reading the account without blowing up the context.

**Three of the reads below are heavier than they look, and one of them is the worst in Phase 0.** `user-find-by-filter {filter: {isAdmin: true}}` returns each admin's full `workspaces` array, so a tenant with a dozen admins across fifty workspaces answers with tens of thousands of characters, larger than anything else here. `workspace-list` has no name filter, and an org-wide `workspace-list-users` returns every member of every workspace. Take the fields you need from each and discard the rest rather than holding the payload: for admins that is email, `licenses.tier` and `lastLogin`; for workspaces the name, id and `nrOfUsers`.

## What to read

- `health-ping` - the credential works and the service is reachable.
- `tenant-get` - tenant identity (subdomain, cluster). Needed for the tenant's public URLs (a Concierge router link, the JS snippet), not for admin links, which are always on the fixed `fire.chilipiper.com` host. Does not return a plan or tier.
- **The live tool list** - what this specific credential can actually do, which is the real ceiling on what you can build. Read it every session; the server gains and renames tools continuously and a scoped key exposes fewer of them than an Admin OAuth grant.
- **Entitlement - read the `tier`, not the booleans.** The per-user `licenses` object (via `user-read` / `user-find`) carries `tier` (`RoutingAndScheduling`, `Experiences`, `ChiliDataPlatform`) alongside the flags `distro`, `chiliCalOrg`, `concierge`, `conciergeLive`, `chat`, `handoff`.
  **The tier is the licence.** Tiers are bundles: a tier contains all the functionality the individual licences do, so a user on `Experiences` has that bundle's products whether or not the matching boolean reads true. `tier` present with every flag false is a **licensed** user and nothing needs confirming. Three states:
  - **Tier present**: that is your answer. Offer what the tier covers and move on. Do not caveat it, do not ask the customer to confirm what they bought, and do not raise a licence check.
  - **No tier but the product flags populated**: read the flags as the entitlement. This is a real state and a whole tenant can be in it, so do not treat it as unreadable. The flags are load-bearing here rather than decorative: distribution members on such a tenant read `Active` rather than `NoLicense`, which is the product agreeing they are entitled. Use them, say once that you read entitlement from the per-product flags because no tier is set, and do not send a licence check to the CSM on the strength of a missing `tier` alone.
  - **No tier and no flags, or the object missing**: genuinely unread, usually a scoped key or an old user record. Say plainly that you could not read it, ask which products they bought, mark it unverified in the plan, and put a licence check on the CSM handoff.
  **Never say "no X licence exists" because a boolean is false on a user who holds a tier.** Where the tier covers that product the host is licensed whatever the flag says, and a booking failure is a calendar or availability problem instead. That rule is about a false flag sitting underneath a tier; it does not apply in the second state above, where the flags are all you have and are the right thing to read. `user-update-licenses` takes `tier` too, and the tier is the part it honours.
  **What each tier contains is on `chilipiper.com/pricing`.** Read it rather than reciting a bundle from memory. One thing holds across all of them: **ChiliCal is included with every seat on every tier**, so scheduling links are never a tier-upgrade conversation. `ChiliDataPlatform` is the newest tier, so a customer asking for it is a CSM conversation rather than a build.
- **CRM type and connection status** - the org connection status (CRM, calendar, Slack, Gong, Outreach) and per-user `salesforce` / `hubspot` linkage. **No CRM connected** means guide them to connect Salesforce or HubSpot at `https://fire.chilipiper.com/fire/admin/integrations/built-in`. **Both connected** means use the sales reps' source of truth (marketing often runs HubSpot while sales runs Salesforce; use Salesforce). This sets a hard branch: **Distro, the CRM-triggered router product, is Salesforce only**, so a HubSpot org uses Concierge / Handoff / ChiliCal / Chat instead. Distributions are not part of that branch: they are a workspace asset that every motion assigns through, on any CRM.
- **Calendar, read correctly.** Two different things share the word, and conflating them produces a false alarm. **Per-user calendar** is what availability actually depends on: each rep connects their own from MyApp, up to six (help 44647649661971), and no Admin can do it for them. **Company-level calendar integration** is a separate optional tenant integration (help 27275421055379): it reads free/busy for users who have not connected, it never *creates* a meeting, and it only helps Handoff Scheduler (Instant Booking, Suggested Times, inserted links) and internal additional guests. It explicitly does nothing for Concierge and nothing for a ChiliCal team link, and it is not a fallback user.
  So **do not report "0 calendars connected" as a failed prerequisite.** On a fresh org it is the normal state, and the fix is end-user setup (Phase 4), not an Admin action today. Say what each one covers, then ask the one thing that unblocks this session: will the Admin in front of you connect their own calendar, so the booking surface you build can be tested end to end before they roll it out. Pair it with the admin ladder below: a connected calendar on a user with no tier still leaves you nothing to test against.
- **Who the admins are, and whether they are licensed.** `user-find-by-filter` with `{filter: {isAdmin: true}}` returns per admin their `licenses`, `isSuperAdmin`, `workspaces`, `connections` and `lastLogin`. Licensed here means **holding a tier**, not holding a true boolean. Work the ladder:
  - **Every admin already on a tier** - nothing to do, move on. Do not raise it.
  - **Exactly one admin** - assume that is the person you are talking to. Say so rather than asking, because the assumption can be wrong: the credential may belong to someone else entirely.
  - **Several admins, some with no tier** - ask which one they are, once.
  An operator with no tier has no availability and cannot host, so nothing you build can be tested end to end. Where one is needed, assign it as the first write of the build (Phase 3), not as a tidy-up at the end.
  **On a whoami: the reads have none, but the first write does.** Nothing in the read surface tells you who the credential authenticates as, which is why the ladder above exists. Every create response carries `metadata.createdBy`, though, and it names the caller outright: a user id, or `mcp/api_<prefix>` where the session is running on a scoped API key rather than anyone's OAuth. Once you have built the first asset, use that instead of the assumption, and correct the record if the ladder guessed wrong.
- **Write capability** - can this session create config (Admin OAuth, or a write-scoped key) or is it read only? **There is no probe for this.** The only signal is that write tools carry `readOnlyHint: false` in the live list, which describes the catalogue rather than your key. Report it honestly ("write tools are exposed, unconfirmed until the first write succeeds") instead of claiming a check you did not run. Write-capable goes to a live build in Phase 3; read-only produces the plan plus a CSM handoff for a write-scoped key.
- **Which workspace to build in, decided here.** Assets are ring-fenced per workspace, so this choice scopes everything after it. `workspace-list` returns each workspace with `nrOfUsers`, and has no filter or pagination, so on a cluttered tenant it is an expensive read: take the name and id and discard the rest.
  - **One workspace** - use it. Every tenant is provisioned with a default workspace, and that is where the overwhelming majority of builds belong.
  - **Several** - ask which. **Do not guess from names or user counts**, and do not infer it from which one looks busiest: a test workspace can out-populate the real one, and building in the wrong place means every asset is invisible to the people who need it.
  - **Several, more than a handful** - an older tenant can carry fifty, which no four-option menu can represent. Do not force it into one: ask as open text, offer the largest few by `nrOfUsers` as a prompt, and say the list is partial and any other name is fine. That keeps the decision theirs while giving someone who does not know the answer somewhere to start.
  - **A new workspace** is a deliberate choice to separate teams or business units, not a routine branch, and it is rarely the right answer during onboarding. If the customer wants one anyway, they create it in Command Center at `/fire/admin/workspaces` and give you the id; search the `workspace` category first in case a create tool has since landed.
  Once chosen, **scope every subsequent read to it**: `distribution-list-put {workspaceIds: [id]}`, `rule-list {filter: {workspaceId: id}}`, and the same for teams and meeting types. That is what keeps a cluttered tenant readable.
- **What already exists in that workspace** - `workspace-list-users`, `team-list-put`, plus scoped counts of distributions, rules and meeting types. Reuse what clearly matches; do not adopt unnamed or empty assets (`shared-assets.md` § Reuse or create).
