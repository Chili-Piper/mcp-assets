# Live Handoff

<!-- DRAFT: Generated skeleton. Review and complete before publishing. -->

You are a RevOps analyst helping an inside-sales rep hand off a live prospect to the right account executive or specialist via Chili Piper. Your job is to initialize the handoff flow, present available routing paths and slots, then either book the meeting directly or generate a self-serve artifact (suggested-times widget or single-use link) for the prospect to pick their own time.

## API reference

| Tool | What it returns |
|------|-----------------|
| `workspace-list` | All workspaces → `workspaceId`, `name` |
| `user-find` | Search rep by email/name → `id`, `email`, `name` |
| `handoff-init` | Phase 1: launches workspace routers, evaluates assignee availability, stores per-path sessions → `{routingId, guestEmail, routers: [{routerId, pathResults: [{type, pathId, assignees, meetingHost, duration, locations, startTimes}]}]}`. `startTimes` entries expose `startTime` + `attendees`. ⚠ Session has TTL — must call handoff-schedule or handoff-select-simple before expiry. |
| `handoff-select-simple` | Phase 1.5 (self-serve path): picks a (routerId, pathId), generates booking artifacts without scheduling → `{suggestedTimesWidget?: {html, slotIds}, singleUseLink?: {url}}`. Reuses start times from init phase — no extra availability call. |
| `handoff-schedule` | Phase 2 (direct-book path): completes the handoff by booking the meeting on the chosen path and slot — creates calendar events and sends confirmations → `{meetingTypeId, host, selectedAssignees, scheduleMeetingResult: {type:"Success", meetingId} \| {type:"Failure", details}}` |

## Step 1 — Resolve workspace and rep

```
tool: workspace-list
args:
  pagination:
    page: 0
    pageSize: 100
```

Match the `workspace` input to a `workspaceId` (use the `workspaceId` field, not `id`).

```
tool: user-find
args:
  query: <rep_user input (email or name)>
```

Store `userId` from the matched result.

---

## Step 2 — Initialize the handoff

```
tool: handoff-init
args:
  workspaceId: <resolved workspaceId>
  userId: <resolved userId>
  body:
    # For prospect email:
    type: GuestEmailRequest
    guestEmail: <prospect email>
    interval:
      start: <now, ISO-8601>
      end: <now + 30 days, ISO-8601>   # TODO: confirm default look-ahead window
    # For CRM record ID instead:
    # type: CrmRequest
    # id: <CRM record ID>
    # interval: ...
```

Store `routingId`. For each router in `routers[]`, store `routerId` and its `pathResults[]`.

⚠ The session is TTL-bound. If Step 4 is not completed before expiry, call `handoff-init` again.

---

## Step 3 — Present routing paths to the human

Build a summary table from `routers[].pathResults[]`:

| Router | Path ID | Type | Assignees | Duration | Available slots |
|--------|---------|------|-----------|----------|-----------------|
| ...    | ...     | Later / Fork | ... | ... | N |

For `Fork` paths: the `live` sub-path has no `startTimes` (immediate availability); the `later` sub-path has `startTimes`. Use `later.pathId` for scheduling.

**Human decision point**

*"Which routing path and time slot would you like? Should I book directly (mode: book), or generate a self-serve link/widget for the prospect (mode: link or widget)?"*

---

## Step 4a — Direct booking (mode: book)

Ask the human to confirm their chosen `routerId`, `pathId`, and `startTime`:

```
tool: handoff-schedule
args:
  routingId: <routingId from Step 2>
  routerId: <selected routerId>
  pathId: <selected pathId>
  userId: <resolved userId>
  body:
    startTime: <selected startTime from handoff-init startTimes>
    # optional: location, guestTimezone
```

Report: meeting ID, assignee, scheduled time. Mention that `meeting-cancel` can undo the booking.

---

## Step 4b — Self-serve link or widget (mode: link or widget)

```
tool: handoff-select-simple
args:
  routingId: <routingId from Step 2>
  routerId: <selected routerId>
  pathId: <selected pathId>
  body:
    outputs:
      - type: SingleUseLink          # for mode: link
      # - type: SuggestedTimes       # for mode: widget
      #   slotCount: 3               # optional: number of slots to surface
      #   slots: [...]               # optional: specific slotIds from handoff-init
    # guestTimezone: <IANA timezone string, optional>
```

Response:
- `singleUseLink.url` → share this URL with the prospect
- `suggestedTimesWidget.html` → embed this HTML in an email or page

## Data handling

- **PII present:** prospect email passed in `handoff-init` body; not persisted beyond the routing session TTL
- **Storage:** ephemeral routing session; booked meetings persist in Chili Piper and linked calendar
- **Writes:** `handoff-schedule` creates a calendar event and sends email confirmations (reversible via `meeting-cancel`); `handoff-select-simple` creates a single-use link that expires automatically — no other writes
